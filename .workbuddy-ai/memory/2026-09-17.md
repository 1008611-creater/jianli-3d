### 关键技术决策与踩坑

**1. 模型归一化（最关键的一次误判）**
最初以为 GLB 是 ±32767 单位，实际 GLTFLoader **已自动应用 node.scale 0.49**，
加载后仅约 (0.64, 0.98, 0.97)。最终 `MODEL_SPAN = 1.45`，用包围盒居中+缩放。

**2. 相机 fov**
fov=32 时视野高度仅 0.83 < 模型高 1.0 → 只看到脸部特写。**改为 fov=45**。

**3. 贴纸吸附（核心难点）**
贴纸锚点位于「半径 0.5 的参考球面」，而模型是椭球（y 半轴 0.725、x 半轴仅 0.475），
直接放锚点会飘在体外/堆叠。**解法：只用锚点的「方位语义」**——取法线方向为方位，
从模型外侧沿 -normal 射线投射求交，命中点即真实表面，朝向对齐命中面法线；
未命中时投影到外接椭球兜底。

**4. HDRI 必须本地化**
drei `Environment preset="city"` 会联网拉 raw.githack.com 的 HDR，fetch 失败会
**炸掉整棵 3D 树导致全页白屏**。改用 `files="/assets/env/city.hdr"`（从
raw.githubusercontent.com/pmndrs/drei-assets 下载，CC0）。注意属性名是
`environmentRotation` 而非 `rotation`。
另加 ErrorBoundary 隔离 3D 层失败，并保证失败时载入屏也收起。

**5. 顶部角落信息与品牌栏重叠**
`.corner-tl` 原本用 `translateY(-100%)` 放到框外上方 → 与 `.top-bar` 撞车。
改为落在框内（`top:10px; left:12px`）。

### 无头 Chrome 截图排查（值得记住的方法论）
现象：`?s=0.4` 等带滚动参数的 URL 截图为纯背景色（5292~6303 字节），
不带参数正常（501KB）。**一度怀疑是自己的滚动代码有 bug。**

排查结论（用 CDP 逐项测量，别靠猜）：
- DOM/布局**完全正常**：`.ui-layer` 1592×753、timeline 在右边缘、canvas 已尺寸化、
  载入屏已 is-hidden、无任何 console 错误
- `scrollY` 正确应用（0.5 → 2156 / max 4305）
- `#`、`#top`、`#zzz`、`?zzz=1` 全部正常渲染 → 不是 fragment/query 机制问题
- **rAF 在无头环境只有 ~2.5 帧/秒**（1200ms 内 3 次），SwiftShader 软件光栅化
  无法在截图窗口内完成一帧 Bloom+DOF 渲染
- `gl.readPixels` 在合成后返回全 0（`preserveDrawingBuffer:false`），**不能用作探针**

结论：**纯属无头软件渲染的性能假象，真实 GPU 环境无此问题。**
正确做法：用 CDP `Emulation.setDeviceMetricsOverride` 设定真实视口 +
`Page.captureScreenshot`，并给足渲染时间；或用「锁定机位」而非滚动来逐点验证。

附带发现：headless Chrome 在 Windows 上**最小窗口宽度约 500px**，
所以 `--window-size=375,812` 实际是 500px 布局 —— 要测真手机视口必须用 CDP 设备模拟。

### 新增能力
`#stop=<n>` 深链：把镜头锁定到第 n 个 stop（0=封面），便于分享章节与逐节校对构图。
实现：`CameraRig` 增加 `pinnedIndex`，`App` 从 hash 解析。

### 响应式
新增 `max-width:640px` 断点：隐藏 `.corner-tl/tr`、`.brand-sub`、`.timeline`，
收窄内边距，链接胶囊限宽省略。验证 375px 无横向溢出（`overflowX:false`）。

### 验证结论
- 4 个 stop 机位全部渲染成功（502~565KB）：hero 特写 → 正面 → 更近 → 侧面profile → 抬升另一侧
- 作品集 3 分区 14 项 + 页脚正常
- 响应式 375 / 1024 / 1600 三档验证通过

### ⚠️ 磁盘清理最重要的教训
**`ctr images list` 默认查 `default` namespace（空），必须 `ctr -n moby images list`。**
我第一轮只看 default，误判 containerd 的 16G 是"孤儿数据"，差点 `rm -rf` 掉
——实际上那是 **11 个运行中业务容器 + 4 个 RUNNING task** 的活数据。
`docker`（`/var/lib/docker`）与 `containerd`（`ctr -n moby`）是**两套独立存储**，
两边都有活的容器。**绝不要手工删 containerd 目录**，只能用 `ctr images rm` + `content prune`。

## 🔴 线上一直 loading 的根因与修复（同日深夜）

用户报「进去之后一直是 loading 状态」。排查结论：**模型太大 + CDN 不缓存**。

### 根因
1. **模型是 3D 扫描原始网格**：1,939,726 三角形、1,021,941 顶点，
   已用 meshopt 压缩仍有 13.9MB。
2. **服务器上行带宽只有 ~1.1MB/s**（实测 `speed.cloudflare.com`）→
   13.9MB 要 12 秒以上，实测 45 秒只下 897KB。
3. **Cloudflare 默认不缓存 `.glb` / `.hdr`**：
   - `.webp` / `.js` → `cf-cache-status: HIT`
   - `.glb` / `.hdr` → `DYNAMIC`（不在 CF 默认缓存扩展名名单里）
   → 每次访问都回源慢速重传。

### 修复 1：模型简化（13.24MB → 1.26MB，-90.5%）
新脚本 `scripts/simplify-model.mjs`（用 `@gltf-transform` + `meshoptimizer` + `sharp`）：
- 网格简化 6%：194 万面 → **11.6 万面**（-94%）
- 纹理压缩：主纹理 2048→1024（2.94MB → 205KB）
- 几何未破坏：包围盒偏差仅 **0.06%**，贴纸锚点不会错位

用法：`node scripts/simplify-model.mjs 0.06`（预览）/ `--write`（覆盖，自动备份 `me.orig.glb`）

### 修复 1b：HDRI 缩放（1.47MB → 0.29MB，-80%）
1024×512 → 512×256，用 **ffmpeg**（比手写 RGBE 编解码靠谱得多）：
```bash
FF="/c/Users/lsb/AppData/Local/Programs/ffmpeg/bin/ffmpeg"
"$FF" -y -i public/assets/env/city.hdr -vf scale=512:256 -update 1 -frames:v 1 \
  "E:/codex/heikesong3/jianli/public/assets/env/city.hdr"
```
坑：① 必须 `-update 1 -frames:v 1`，否则不写文件；② 输出要用 Windows 绝对路径，
Git Bash 的 `/tmp/x.hdr` 写不出来。
验证：`new RGBELoader().parse(arrayBuffer)` 能解析即 OK（HalfFloatType=1016）。

### 最终成果
**首屏传输量 约 12MB → 1.71MB，加载时间 约 11 秒 → 1.6 秒。**
站点总体积 27MB → **5.0MB**，dist/ 3.4MB。

### 修复 2：ngnix 重复 Cache-Control 头
`expires 30d` 输出 `Cache-Control: max-age=2592000`，
`add_header Cache-Control "public"` 又追加一条 → **响应里出现两个 Cache-Control**，
Cloudflare 视为不可靠**拒绝缓存**。
→ 全部改为单条 `add_header Cache-Control "public, max-age=N" always`。

> 注意：**这个 nginx 修复并没有让 `.glb` 变成 HIT**（仍是 DYNAMIC），
> 因为更根本的原因是 CF 默认不缓存该扩展名。
> 彻底解决需在 CF 控制台加 Cache Rule（见 docs/DEPLOY.md）。
